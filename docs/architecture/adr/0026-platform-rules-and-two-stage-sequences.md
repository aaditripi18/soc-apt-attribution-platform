# ADR-0026 — Platform-authored rules and two-stage sequences

- **Status:** ACCEPTED (2026-10-13, owner instruction following the measurement in ADR-0025 Amendments E and F:
  build a focused detection for a delivered file that is then run, correlating the two events rather than
  treating a file name as proof).
- **Builds on:** ADR-0015 Amendment C (multi-event rules), ADR-0025 (declared versus established), ADR-0003
  Amendment H (enrich tier), CLAUDE.md ("prefer authoritative sources … over manually recreating", "never
  fabricate").

## Why the platform now has rules of its own

Detection content here is translated from published rules. Measured against the dataset authors' own technique
lists, running a delivered file was never counted in seven recordings, and adding the network logs changed nothing
because no pinned rule recognises it (ADR-0025 Amendments E, F). In one recording the delivery was visible only
because a mislabelled rule happened to fire on it. No pinned Sigma or Elastic rule expresses "this file was saved
by a browser and then started": it needs two events linked by the file's path.

So this is an exception to the default, made for a measured gap, and kept visibly separate:
`data/detection/platform/platform-rules.json`, generated by `scripts/build_platform_rules.py`, rule source
`platform:…`, shown on the site with a "platform" badge and no upstream link.

## Decisions

### D1 — A two-stage sequence (`aggregation.kind = "sequence"`)

Two rules of one family. A stage-2 match detects only when a stage-1 match on the **same host** with the **same
key value** preceded it within the span; the detection is anchored on the stage-2 event and names both
Observations. Keys of form `windows_path` compare without case and without an NTFS stream suffix, so the
browser's download marker (`file.exe:Zone.Identifier`) and the file are one key. This is the minimum needed: no
general sequence language, no more than two stages.

### D2 — The two rules

| Rule | Stage 1 | Stage 2 | Tier | Techniques |
|---|---|---|---|---|
| Deceptively named download run by the user | a web browser writes a file | that file starts as a process, and its name ends in a document, image, archive or media extension followed by `.exe` | core | Double File Extension, User Execution: Malicious File |
| File saved by a browser, then run | a web browser writes a file | that file starts as a process | enrich | User Execution: Malicious File |

- The second rule fires on every installer a user downloads and runs. It is context only: shown, never compared.
- The first rule's two techniques are from different families, so by ADR-0025 they would be declared only. Its
  logic is known in full, and the recorded review establishes both: the name is the double extension, and the
  start of a browser-saved file is the user running a delivered file. **It does not establish that the file is
  malicious.**

### D3 — Choices that are this platform's, stated

Six browsers (`msedge`, `chrome`, `firefox`, `brave`, `opera`, `iexplore`); sixteen decoy extensions; a span of one
day between saving and running. A file fetched by another program, run from another host, or renamed in between is
not matched.

## Results

Tool runs (snapshot `data/validation/history/investigations.tool-runs-with-platform-rules.json`), against the same
authors' lists and the saved baseline:

- **16 -> 17 of 45.** One recording has a deceptively named payload (`….jpeg.exe`): Double File Extension and
  User Execution are now counted there (7 -> 9 techniques). In four recordings the payload was saved by a browser
  and run under an ordinary name: recorded as context, not counted. In two, no browser-saved file was run.
- Counting every browser-saved file that is run would give about 21 of 45, and would flag ordinary software
  installs. Not done.

Reference investigations (snapshot `…after-platform-rules.json`): only the uploaded recording changes (7 -> 9
counted; candidates 157 -> 177; top profile Kimsuky 73%, 7 of 9). No verdict changes; APT29 still identified;
known actors still at positions 14–124.

## What remains undetected, and why

A delivered payload with an ordinary name is indistinguishable, in host logs, from a legitimate download. Telling
them apart needs more than the name: what the file does next, or the network side (an executable arriving from an
unfamiliar address — the executable-file log the Zeek reader does not yet read). Both are separate work.

## Checks

`tests/test_platform_rules.py`: the deceptive download detected on the execution, naming both events, both
techniques established under the review and declared only without it; an ordinary download context only; seven
cases that must not detect (name alone, saved never run, run before saved, more than a day, another host, saved by
a non-browser, a different file run); the tracked pack is what the builder writes; malformed sequences refused;
the site's label takes its tier from the detecting stage. Served-model audit on a re-run with core and enrich
platform evidence: every check passes.

## Amendment A (2026-10-18) — the network side: an executable received over HTTP

**Rule.** `platform:executable-received-over-http`, one event: Zeek's file analysis records a file of MIME type
`application/x-dosexec` delivered over HTTP to the connection's originator (`is_orig` false — a download, not an
upload). Ingress Tool Transfer, **enrich tier**: ordinary software downloads look the same. The network reader now
keeps the `files` log's `is_orig` (`ZeekRef.file_is_orig`). Zeek writes booleans as `T`/`F` in its TSV logs and
`true`/`false` in JSON; the reader keeps them as written (its documentation said `true`/`false` only), and the
rule accepts both.

**Where it fires.** Six of the seven tool runs, each on the payload fetched from the lab's attack server; not in
the seventh, whose capture holds no executable transfer. Tests: an upload, a non-executable and a non-HTTP transfer
do not fire.

**Measured effect** (seven tool runs with their network logs; snapshot
`data/validation/history/investigations.tool-runs-with-network-rule.json`; audit 12,680 checks, all passing): **no
change to what is counted** — expected, since it is context. The two techniques gained on the recording with the
deceptively named payload come from the host rule above, not from this one.

**A limit this exposed.** Context Evidence is shown only inside activity clusters, and enrich Evidence never forms
one on its own. Network Observations carry no process identity, so they never link structurally to the host's
clusters. The six detections are therefore stored and counted in "low-level items in no unit" but **appear on no
investigation page**. Making them visible needs either a place for Evidence outside clusters, or linking network
and host events (by address and time), which ADR-0003 deliberately does not do on shared attributes alone. Not
decided here.

## Amendment B (2026-10-18) — context outside the activity clusters is shown

**Decision.** The limit found in Amendment A is closed by display, not by linking. The investigation record now
lists the Evidence that belongs to no unit (`evidence_outside_unit_ids`, schema `investigation/3`), and
`GET /investigations/{id}/context` serves it in time order: when, which host, what was seen (process name or
action, never a command line), the technique, network endpoints and file type where the event has them, and the
rule. The investigation's overview shows it in a "Context outside the activity clusters" table, also when an
investigation has no cluster at all. Nothing in it is compared with group profiles; the page says so.

Network and host events are still **not** linked by address and time: sharing an address is a weak link, and
ADR-0003 keeps correlation to structural links. The analyst sees both and can relate them.

**Checks.** `tests/test_context_evidence.py` (a recording whose only Evidence is low-level: listed as context, not
in the activity; an investigation with everything in clusters has no context); the served-model audit checks that
the context lists exactly the Evidence outside units and none of the units' Evidence.
