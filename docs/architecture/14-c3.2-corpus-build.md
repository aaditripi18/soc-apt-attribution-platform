# 14 — C3.2 corpus build (first implementation slice)

**Status:** first-slice implementation note (2026-09-21). Ratifies the approved
C3.2 corpus-build specification for its **first slice only**. Authoritative
methodology is ADR-0006 (§D5/§D6/§D8/§D9/§D10/§D13) and the B1-M/B1-D locks; this
note records how the first slice realises it and where the boundary sits. It
changes no accepted decision.

## Tier boundary (binding)

This slice builds a **Tier-1 machinery corpus** from **declared-provenance
SYNTHETIC/REPLAY** fixtures. **It is not real-world attribution-accuracy
evidence** (ADR-0006 §D11 documentation-relative ceiling; §D14 real-vs-synthetic
boundary). Real-incident (Tier-2) data remains accuracy-validation-only and is
**not** part of this slice. No calibration result — and nothing derived from this
corpus — may be read as a real-world attribution or false-attribution rate.

## What the first slice delivers

- `src/attribution_platform/calibration/corpus_builder.py` — the corpus builder:
  it replays labeled fixtures through the **existing, unmodified** pipeline
  (`replay_fixture_through_behavioral_sequences`), assembles frozen
  `CalibrationCase` objects from the produced `(CorrelationGroup,
  BehavioralSequence)` plus the separately-authored annotation, and builds a
  `CalibrationCorpusManifest` whose `calibration_corpus_version` comes from the
  **existing** `compute_calibration_corpus_version` (via `from_cases`) — **no
  second hashing mechanism**.
- `data/calibration/corpus/seed/` — a tiny illustrative **2–3-family** seed
  corpus (raw-telemetry fixtures in `scenarios/`, separately-authored labels in
  `annotations/`), proving the builder and replay path end-to-end.
- `tests/test_calibration_corpus_builder.py` — determinism / PYTHONHASHSEED
  independence, id-preservation (not fabrication), manifest + version via the
  existing mechanism, non-mutation, and fail-closed behaviour.

## Boundaries (explicit)

- **Labels are separate from telemetry.** Ground truth and expected-output
  shapes live in `annotations/`, never in the raw-telemetry fixtures, and are
  **never** derived from ATT&CK `uses` relationships (§D6 anti-circularity).
  Expected-output bands are **opaque authored tokens**, never numbers.
- **One family, one case.** Each fixture replays to exactly one attribution unit
  in this slice; fixtures producing zero or several groups fail closed. The
  general multi-group mapping belongs to the later full C3.2 gate.
- **Not the golden corpus.** This seed deliberately does **not** satisfy the full
  §D19 category-completeness acceptance gate; the category-completeness validator
  and the complete, split-balanced, blind-actor-bearing corpus are the later full
  C3.2 gate.

## Explicit non-goals (unchanged)

This slice implements **no** fitting, `calibration_version`, likelihood,
confidence, WEP, abstention, scoring, or G3.6, and modifies **no** candidate
generation, ACH, comparative analysis, CoverageProfile, `evidence_type`
implementation, replay pipeline, existing Type-A fixtures, or frontend.

## Stage 2 decisions (2026-09-22)

### D1 — evidence-type coverage → resolved by an isolated calibration rule pack

**Finding (verified).** The core detection pack `fixtures/phase1_core_rules.json`
emits only `BEHAVIORAL` (5 rules) and `CONTEXTUAL` (1 rule,
`platform-interactive-logon`); it emits **no** `EVIDENTIARY` or `PROCEDURAL`.
`EvidenceType` is inherited from the firing rule
(`DetectionRule.evidence_type` → `DetectionResult.evidence_type` → derived
`Evidence.evidence_type` → `BehavioralStep.evidence_types`, B4); a rule may
declare any `EvidenceType` and carry zero technique mappings.

**Decision.** Add a small, isolated **Type-B calibration rule pack**,
`data/calibration/rules/calibration_evidence_type_rules.json`, with exactly two
deterministic single-Observation rules: one `EVIDENTIARY` (a corroborating
infrastructure IOC — a documented `network.destination.ip`, no technique
mapping) and one `PROCEDURAL` (a specific command-line procedure detail —
`process.command_line contains "DownloadString"`, no technique mapping). The
existing core pack is **not** modified (ADR-0006 §D8 keeps `fixtures/*` Type-A
structural). Corpus builds that need all four types run detection with the core
pack **plus** this extension; both types are emitted by the **real, unmodified**
detection/evidence/correlation pipeline and flow onto `BehavioralStep.evidence_types`
— never fabricated in the corpus builder or annotations. Tests
(`tests/test_calibration_evidence_type_rules.py`) prove genuine emission and that
all four `EvidenceType` values are reachable across the two packs.

**Boundary.** No replay-pipeline change, no detection-engine change, no frozen
B1/P1/P2/P3/B4 contract change, no scoring/attribution change. The extension is
detection *content* (a data artifact), tracked under the existing
`!/data/calibration/` .gitignore exception.

### D2 — final-test population → `EXCLUDED` convention (no contract change)

**Finding (verified).** `CaseRole` = {`CALIBRATION`, `HELD_OUT_VALIDATION`,
`BLIND_ACTOR_HOLDOUT`, `TIER1_STRUCTURAL`, `EXCLUDED`}. There is **no**
`FINAL_TEST` role.

**Decision.** The §D9 "FINAL TEST" population is represented by **`EXCLUDED`**
(final-test-reserved): families held out of all calibration/validation
operations until a one-time final evaluation. The frozen B1.2 `CaseRole` enum is
**not** modified to add `FINAL_TEST` — `EXCLUDED` already carries the required
"reserved / used in no calibration operation" semantics, and amending a frozen
contract for a nameable convention is unwarranted. This convention is what later
split/acceptance tooling treats as the final-test population.

**Out of scope of Stage 2.** No full v1 corpus authoring, no category validator
(Stage 3), no fitting, `calibration_version`, scoring, WEP, abstention, G3.6,
candidate-generation/ACH/comparative/CoverageProfile change, or frontend.

## Stage 3 decision (2026-09-22)

### D3 — category-completeness validator → additive `CaseCategoryRecord`, not a `CalibrationCase` field

**Finding (verified, reported before implementing).** Nothing in the frozen
`CalibrationCase` / `GroundTruth` / `ExpectedOutputShape` /
`CorpusCaseEntry` / manifest chain carries a repetition-sub-type,
correlated-detection, genuinely-distinct, deliberate-imitation, or
campaign-contextualization tag, nor a per-case `EvidenceType` set —
`CalibrationCase` intentionally holds only Phase 0–2 *id references*, never a
copy of `BehavioralStep.evidence_types`. Two of the nine "category presence"
items *are* directly derivable from the existing contract without any new
metadata: the four `LabelSemantics` values (read from
`ground_truth.label_semantics`) and coverage-present/coverage-absent (read
from whether `coverage_assumptions` is non-empty/empty).

**Decision.** `src/attribution_platform/calibration/category_validation.py`
implements `validate_category_completeness(manifest, cases, category_records)`
— read-only, additive, over a new, separately-authored `CaseCategoryRecord`
per case (`case_id` + `categories: tuple[CaseCategoryTag, ...]` +
`evidence_types: tuple[EvidenceType, ...]`), mirroring the same
anti-circularity separation the Stage 1 builder already established between
raw telemetry and its `CorpusScenarioAnnotation`. `CalibrationCase` is **not**
modified. A record is an authored declaration of an already-observed fact
about a real, already-built case — never fabricated or ATT&CK-inferred by the
validator. Checks: all nine `CaseCategoryTag` values, all four
`LabelSemantics` values (present in both `CALIBRATION` and
`HELD_OUT_VALIDATION` specifically), all four `EvidenceType` values, both a
coverage-present and coverage-absent case, and every required population
(`CALIBRATION`/`HELD_OUT_VALIDATION`/`BLIND_ACTOR_HOLDOUT`/`EXCLUDED`)
non-empty. A `(manifest, cases, category_records)` `case_id`-set mismatch
fails closed.

**Boundary.** No `calibration/__init__.py` change (matching the Stage 1
`corpus_builder.py` precedent — the C3.2 track is not re-exported through the
B1.x package surface). No split/leakage or provenance/license duplication
(B1.4/B1.5 own those). No fitting, `calibration_version`, scoring, WEP,
abstention, G3.6, or ATT&CK dependency. Authoring real `CaseCategoryRecord`
values for the actual seed/golden corpus is deferred to Stage 4.

## Stage 4 (2026-09-22)

**v1 corpus:** `data/calibration/corpus/v1/` — 18 scenario families / 18
`CalibrationCase`s, built through the existing, unmodified
`corpus_builder.build_corpus_from_dir` and passing the existing Stage 3
category-completeness validator, B1.4 split validator, and B1.5 provenance
validator unmodified. See `data/calibration/corpus/v1/README.md` for the full
family/split/actor/category/evidence-type/coverage design and the explicit
§D11 documentation-relative-ceiling statement (repeated there, not only
here, since that file is the one a corpus consumer is most likely to read
first).

**Stage 3 interpretation preserved, not changed.** Before authoring, Stage 4
re-verified ADR-0006 §D19 directly: it states the repetition/evidence
category list in prose only, with no machine-checkable enumeration and no
per-population (CALIBRATION vs HELD_OUT_VALIDATION) presence rule. The Stage
3 validator's 9-tag `CaseCategoryTag` taxonomy and its CALIBRATION+
HELD_OUT_VALIDATION presence requirement is this project's own prior
operationalization of that prose (recorded, with its own interpretation
note, in Stage 3's implementation report) — Stage 4 did not re-derive or
change it, and did not touch `category_validation.py` or any frozen
contract. The v1 corpus was authored to satisfy the *existing* validator.

**One new interpretation was required and is documented, not silently
folded in:** the real replay pipeline requires **at least two** distinct
pieces of technique/rule-matched evidence to form any `CorrelationGroup`/
`BehavioralSequence` — an isolated single piece of evidence never reaches
group status (verified empirically against the real, unmodified pipeline;
this is a platform-mechanism fact, not a decision). "One-observation"
families are therefore authored as **two distinct techniques, each observed
once** (the sparsest case the real pipeline can produce), contrasted with
"repeated-behavior"/"repeated-detection" families where the **same**
technique/rule fires multiple times. This does not change
`category_validation.py`'s semantics (`CaseCategoryTag.ONE_OBSERVATION` is
still an opaque authored tag); it only records how the v1 corpus honestly
satisfies it given the pipeline's real minimum.

**Evidence-type extension usage.** `v1-cal-charlie-correlated` and
`v1-hov-delta-correlated` each chain the unmodified core pack with the
unmodified Stage 2 calibration extension pack in one family, so all four
`EvidenceType` values are reached; every family's `CaseCategoryRecord.
evidence_types` is captured from that family's own real replay output, never
hand-declared.

**`sources/sources.json` and `manifest.json` are new, generated audit
artifacts** (not present in Stage 1's seed corpus, which never persisted
one) — human-readable snapshots of the one `CalibrationCorpusManifest` object
`build_corpus_from_dir` produces from `scenarios/`+`annotations/`. The
version string inside `manifest.json` is `compute_calibration_corpus_version`'s
own output, persisted for readability; it is not a second identity
mechanism, and rebuilding from `scenarios/`+`annotations/` remains the
authoritative operation (see the v1 README for the exact framing).

**Boundary.** No fitting, `calibration_version`, scoring, WEP, abstention,
G3.6, ATT&CK/attribution/replay-pipeline change, or frozen-contract change.
No real incident data, no live emulation, no fabricated telemetry
provenance, no fabricated ATT&CK evidence mapping, no accuracy claim.

## Stage 5 — corpus → decision-quantity harness (2026-09-24)

**Delivered:** `calibration/decision_inputs.py`. For each frozen `CalibrationCase`
in caller-named roles it replays the case's own fixture, **fails closed unless
the replay reproduces the frozen `correlation_group_id`/`sequence_id` under the
same `attack_kb_version`**, runs the real Gate 3.3–3.5 stages (candidates → ACH
matrix → comparative analysis) plus the Amendment-B `Unattributed` baseline, and
pairs them with the case's authored labels (copied verbatim, never mapped onto
ATT&CK candidates). `EXCLUDED` (final-test-reserved) is refused.
`compute_case_decision_quantities(input, min_profile_floor=…)` evaluates any grid
floor without re-replaying: the fields the decision layer reads (`d_value`,
`g_value`, `profile_breadth`) are floor-independent (tested).

**Boundary.** No fitting, no chosen numeric value, no `calibration_version`, no
G3.6 decision.

### Observed on v1 (facts from the real run — these gate the fitting sub-gate)

16 evaluable cases (7 calibration, 7 held-out, 2 blind-actor). Every case with
features has 1–2 distinct observed features and 53–151 ATT&CK candidates.

- **F5-1 — ranking retention is not computable on v1.** Authored actor labels are
  synthetic emulation identities (`EMU-ALPHA` …); candidates are real ATT&CK
  Groups/Campaigns. There is no authored mapping between them, so the F-3
  objective's second term ("maximize ranking retention") has no ground truth.
  Only the abstention-shape term (expected `leading_hypothesis` vs
  `insufficient_evidence`) is evaluable.
- **F5-2 — `concentration` is degenerate.** The top candidate's
  `concentration` is `1.0` in every non-empty case (1–2 features ⇒ one
  contributor dominates). A `τ_concentration` fit has no variation to learn from.
- **F5-3 — calibration and held-out cases share identical feature sets.**
  `v1-cal-unresolved-actor` ≡ `v1-hov-bravo-ingress`, `v1-cal-bravo-lsass-repeat`
  ≡ `v1-hov-delta-correlated`, and both echo-imitation cases ≡
  `v1-cal-alpha-ingress` in every decision quantity. Families are disjoint by
  `scenario_family_id` (so split validation passes), but the held-out gate is
  not independent in *evidence*. Imitation cases being identical is intended;
  the other two pairs aren't.
- **F5-4 — no hard negatives.** Both `unattributable_by_design` cases have zero
  observed features (trivially abstain). No negative case contains common,
  low-diagnosticity techniques, which is exactly what `τ_separation` must
  separate from real attribution.

Per ADR-0006 F-3 "insufficient-data behavior — fail-closed", fitting on v1 as-is
would be degenerate. These findings are recorded, not resolved here; resolving
them (corpus v2 and/or an authored label↔candidate evaluation rule) is an owner
decision before the fitting sub-gate.
